# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

A minimal, opinionated Terraform boilerplate for provisioning Azure infrastructure. It is a
template repo — the goal is to keep it generic, modular, and easy to fork for a real project.
Currently it provisions a single `azurerm_resource_group` with a conventional tags module; new
resources are expected to be added by consumers of the template.

## Repo layout and naming conventions

- Root `*.tf` files use a numeric prefix that indicates load/conceptual order for resources,
  e.g. `1_rg.tf` (resource group). When adding a new resource, follow this pattern (e.g.
  `2_<resource>.tf`) rather than dumping everything into one file.
- Files prefixed with `_` (`_providers.tf`, `_backend.tf`, `_variables.tf`) are cross-cutting
  config, not resources: provider/version constraints, remote backend block, and shared variable
  declarations. Keep this separation — don't declare variables or provider blocks inside a
  numbered resource file.
- `modules/tags/`: a small reusable module enforcing "conventional tags". Its input variable
  `conventional_tags` **requires** an `Application` key (validation block in
  [modules/tags/variables.tf](modules/tags/variables.tf)); `Environment` is set by convention too.
  Any new resource should get `tags = module.main_tags.conventional_tags` (or extend the map)
  rather than inventing ad-hoc tags.
- `environments/<workspace>/`: per-workspace config, currently `nonprod` and `prod`. Each has:
  - `backend.tfvars` — remote state backend args (`storage_account_name`, `resource_group_name`,
    `container_name`, `key`) for `terraform init -backend-config=...`.
  - `variables.tfvars` — input variable values (`subscription_id`, `resource_group_name`,
    `location`) for `terraform plan/apply -var-file=...`.
  - These files ARE tracked in git (only `**/local.tfvars` is gitignored). The committed
    `subscription_id` values are placeholders (`xxxxxxxxxxxxx`) — never replace them with a real
    subscription ID in a tracked file; real/sensitive values belong in an untracked
    `local.tfvars` or CI/CD secrets, not in `environments/*/variables.tfvars`.
- The workspace name is not hardcoded: `.env` sets `TF_WORKSPACE` (currently `nonprod`), and
  Taskfile templates (`{{.TF_WORKSPACE}}`) resolve `environments/<workspace>/backend.tfvars` and
  `variables.tfvars` automatically. Terraform also reads `TF_WORKSPACE` natively, which
  overrides `terraform workspace select/new` — so `.env` is the single source of truth. Switch
  environments with `task tf:workspace:select NAME=<name>` (rewrites `.env`), never with a raw
  `terraform workspace select`. Adding a new environment means adding an `environments/<name>/`
  folder with both files, then `task tf:workspace:create NAME=<name>`.
- Inside `.tf` files, use `terraform.workspace` for per-environment values (e.g. the
  `Environment` tag in `1_rg.tf`) rather than hardcoding an environment name.

## Task runner (go-task)

All common operations are driven by [Taskfile.yml](Taskfile.yml), which includes namespaced task
files from `.tasks/`: `tf`/`terraform` ([TerraformTasks.yml](.tasks/TerraformTasks.yml)),
`docs` ([DocsTasks.yml](.tasks/DocsTasks.yml)), `costs` ([CostsTasks.yml](.tasks/CostsTasks.yml)),
`security` ([SecurityTasks.yml](.tasks/SecurityTasks.yml)), `install` ([InstallTasks.yml](.tasks/InstallTasks.yml)).

Prefer running tasks over raw `terraform` commands so the correct `-var-file` /
`-backend-config` for the active workspace is always used:

```ps1
task                      # list all tasks
task tf:init              # terraform init -backend-config=environments\<ws>\backend.tfvars
task tf:validate           # terraform validate
task tf:lint               # tflint
task tf:plan               # plan + write plan.tfplan and plan.tfgraph (json)
task tf:apply               # apply with the workspace's variables.tfvars
task tf:apply:approve       # apply -auto-approve plan.tfplan (requires a prior tf:plan)
task tf:destroy
task tf:unlock ID=<lock-id>
task tf:workspace:select NAME=<name>   # writes TF_WORKSPACE=<name> into .env
task tf:workspace:create NAME=<name>   # terraform workspace new + writes .env
task docs:generate          # terraform-docs -> Terrraform.md (see below)
task security:scan          # checkov -d .
task costs:analysis         # infracost breakdown + report
```

- `plan.tfplan` / `plan.tfgraph` and all `*.tfstate*` files are build artifacts — never commit
  them (already gitignored).
- This project currently targets **Windows only** (backslash paths in Taskfile vars, Chocolatey/
  winget install tasks). Don't introduce Unix-only assumptions without checking `Taskfile.yml`'s
  path templates.

## Documentation generation

`Terrraform.md` (yes, three r's — that's the actual, existing filename; don't rename it) is
generated by `task docs:generate` via `terraform-docs`, configured in
[.terraform-docs.yml](.terraform-docs.yml). It wraps content between
`<!-- BEGIN_TF_DOCS -->` / `<!-- END_TF_DOCS -->` markers and prepends/appends
[.docs/header.md](.docs/header.md) / [.docs/footer.md](.docs/footer.md). Never hand-edit the
generated table content in `Terrraform.md` — edit variable/output descriptions in the `.tf`
files (or the header/footer files) and regenerate instead.

## When adding a new resource

1. Create a new numbered root file, e.g. `2_storage.tf`.
2. Declare any new input variables in `_variables.tf` (with `type` and `description`).
3. Add matching values to **both** `environments/nonprod/variables.tfvars` and
   `environments/prod/variables.tfvars` (placeholder values are fine for anything sensitive).
4. Apply `module.main_tags.conventional_tags` (or a resource-appropriate tag map derived from it)
   as the resource's `tags`.
5. Run `task tf:validate` and `task tf:lint` before proposing `task tf:plan`.
6. Regenerate docs with `task docs:generate` if inputs/outputs/resources changed.

## Security and cost checks

- `task security:scan` runs Checkov against the whole repo — run it after adding/changing
  resources, not just at release time.
- `task costs:analysis` runs Infracost; it needs an Infracost API key configured in the
  environment to work, and writes `infracosts.json` (a generated artifact, don't commit it).

## CI

[.github/workflows/release.yml](.github/workflows/release.yml) only fires on `v*` tags: it zips
the repo (excluding `.git`) and attaches it to a GitHub Release. There is no CI-run
plan/apply/validate pipeline yet — validation is a local/manual responsibility via the tasks
above.
